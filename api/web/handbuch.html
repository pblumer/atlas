Willkommen bei Atlas

Welcome to Atlas

Atlas ist eine Workflow-Engine für BPMN 2.x: Du zeichnest einen Geschäftsprozess als Diagramm, deployst ihn, und Atlas führt ihn Schritt für Schritt aus – zuverlässig, nachvollziehbar und dauerhaft gespeichert. Entscheidungen lagerst du in DMN-Tabellen aus.

Atlas is a workflow engine for BPMN 2.x: you draw a business process as a diagram, deploy it, and Atlas runs it step by step – reliably, traceably and durably stored. Decisions live in DMN tables.

Instanz / Instance Ein konkreter Durchlauf eines Prozesses. Viele Instanzen pro Prozess. One concrete run of a process. Many instances per process.

The chain behind it is always the same: task → job → worker. An automatic task creates a job as the token reaches it, Atlas stores that job durably, and only then may a worker pick it up and touch the outside world. What a worker is exactly – and why there are three levels of it – is in Forms & workers.

Unter der HaubeUnder the hood

Atlas speichert jeden Zustandsübergang als Ereignis in einem append-only Log und baut den Zustand daraus wieder auf. Darum ist jede Instanz vollständig nachvollziehbar und übersteht Neustarts ohne Datenverlust. Neugierig aufs Warum? Siehe Console → Engine und die Architektur-Doku im Repository.

Atlas records every state transition as an event in an append-only log and rebuilds state from it. That's why every instance is fully traceable and survives restarts without data loss. Curious about the why? See Console → Engine and the architecture docs in the repository.

BPMN lernen

Learn BPMN

BPMN (Business Process Model and Notation) ist die weltweite Standardsprache für Prozessdiagramme. Das Schöne: Fachbereich und IT lesen dasselbe Bild. Du brauchst überraschend wenig, um anzufangen.

BPMN (Business Process Model and Notation) is the worldwide standard language for process diagrams. The beauty: business and IT read the same picture. You need surprisingly little to get started.

Das Vokabular in einer Minute

The vocabulary in one minute

  • Events (Kreise) – etwas passiert: Start (dünn), Zwischenereignis (doppelt), Ende (dick). Ein Prozess beginnt mit einem Start- und endet mit einem End-Event.
  • Events (circles) – something happens: start (thin), intermediate (double), end (thick). A process begins with a start and finishes with an end event.
  • Aktivitäten (Rechtecke) – Arbeit wird getan: Tasks (z. B. Service-, User-, Script-Task) und Subprozesse.
  • Activities (rounded rectangles) – work gets done: tasks (e.g. service, user, script task) and subprocesses.
  • Gateways (Rauten) – der Fluss verzweigt oder führt zusammen: exklusiv (X), parallel (+), inklusiv (O), ereignisbasiert.
  • Gateways (diamonds) – the flow splits or joins: exclusive (X), parallel (+), inclusive (O), event-based.
  • Sequenzflüsse (Pfeile) – verbinden die Elemente und geben die Reihenfolge vor.
  • Sequence flows (arrows) – connect the elements and define the order.

Dein erstes Modell

Your first model

Ein lauffähiger Prozess braucht mindestens: ein Start-Event → eine oder mehrere Aktivitäten → ein End-Event, verbunden durch Sequenzflüsse. Sobald du eine Entscheidung brauchst („wenn Betrag > 1000, dann Freigabe"), setzt du ein exklusives Gateway und schreibst die Bedingung als FEEL-Ausdruck an den Ausgangsfluss.

A runnable process needs at least: a start event → one or more activities → an end event, connected by sequence flows. As soon as you need a decision ("if amount > 1000, require approval"), add an exclusive gateway and write the condition as a FEEL expression on the outgoing flow.

Gut lesbare DiagrammeReadable diagrams

Halte den Happy Path auf einer geraden Linie. Führe Alternativen in einer eigenen Spur darüber oder darunter und lass sie an einem Join-Gateway wieder zusammenlaufen. Beschrifte die Ausgänge von Gateways. Ein Diagramm, das kompiliert, aber wie ein Kabelsalat aussieht, ist noch nicht fertig.

Keep the happy path on one straight line. Route alternatives in their own lane above or below and reconverge them at a join gateway. Label the gateway's outgoing flows. A diagram that compiles but looks like a tangle of wires isn't done yet.

DMN lernen

Learn DMN

DMN (Decision Model and Notation) trennt Entscheidungslogik vom Prozessfluss. Statt zig verschachtelte Gateways zu bauen, schreibst du die Regeln als übersichtliche Entscheidungstabelle. Fachbereiche können sie lesen und pflegen. Atlas wertet DMN über die eingebaute Decision-Engine temis (DMN 1.5 / FEEL) aus.

DMN (Decision Model and Notation) separates decision logic from the process flow. Instead of a maze of nested gateways, you write the rules as a tidy decision table. Business teams can read and maintain it. Atlas evaluates DMN through the built-in decision engine temis (DMN 1.5 / FEEL).

Eine Entscheidungstabelle lesen

Reading a decision table

Spalten links sind Eingaben (Inputs), Spalten rechts sind Ausgaben (Outputs). Jede Zeile ist eine Regel: „wenn die Inputs so aussehen, dann liefere diese Outputs". Beispiel – Rabattstufe nach Kundentyp und Bestellwert:

Columns on the left are inputs, columns on the right are outputs. Each row is a rule: "if the inputs look like this, produce these outputs". Example – discount tier by customer type and order value:

KundentypCustomer type (in) BestellwertOrder value (in) RabattDiscount (out)
"premium">= 100015%
"premium"< 100010%
"standard">= 10005%
"standard"< 10000%

Hit Policy – welche Regel gewinnt?

Hit policy – which rule wins?

  • Unique (U) – genau eine Regel darf passen. Der sichere Standard. exactly one rule may match. The safe default.
  • First (F) – die erste passende Regel von oben gewinnt. the first matching rule from the top wins.
  • Collect (C) – alle passenden Regeln, als Liste (optional summiert/min/max). all matching rules, as a list (optionally sum/min/max).
  • Any (A) – mehrere dürfen passen, müssen aber dasselbe liefern. several may match but must all produce the same result.

  2. Create or upload a DMN model in the Modeler and deploy it.
  3. Im Prozess eine Business-Rule-Task setzen und auf die Entscheidung verweisen.

Prozesse designen

Design processes

Vom leeren Diagramm zum durchdachten Modell.

From an empty diagram to a well-thought-out model.

  1. Das Ziel zuerstGoal first

    Formuliere in einem Satz, was der Prozess erreichen soll und wann er fertig ist. Das bestimmt Start- und End-Event.

    State in one sentence what the process should achieve and when it's finished. That fixes the start and end events.

  2. Den Happy Path zeichnenDraw the happy path

    Die ideale Abfolge ohne Sonderfälle – eine gerade Linie von Tasks.

    The ideal sequence without special cases – a straight line of tasks.

  3. Entscheidungen & AusnahmenDecisions & exceptions

    Gateways für Verzweigungen, Boundary-Events für Timeouts/Fehler, DMN für komplexe Regeln.

    Gateways for branches, boundary events for timeouts/errors, DMN for complex rules.

  4. Daten festlegenDefine the data

    Welche Variablen trägt die Instanz? Woher kommen sie (Start-Formular, Task, Worker)?

    Which variables does the instance carry? Where do they come from (start form, task, worker)?

  5. DokumentierenDocument it

    Jedes Element hat im Details-Panel eine Documentation — direkt unter Name und ID. Schreib dort hinein, warum es den Schritt gibt, welche Regel dahintersteht und wer zuständig ist; für den Prozess selbst (nichts ausgewählt) die Zusammenfassung, die man vor dem Diagramm lesen möchte. Der Text gehört zum Modell: die Engine führt ihn nie aus, aber er überlebt Deploy, Export und jede Version — die Dokumentation bleibt also am Prozess statt in einem Extra-Dokument zu veralten. Bei einer User-Task ist er mehr als eine Notiz: die Tasks-App zeigt ihn der bearbeitenden Person über dem Formular als Arbeitsanweisung. Schreib ihn dort also an die Person, die die Aufgabe erledigt. Im Instanz-Replay steht die Doku des gewählten Elements unter seinen Eigenschaften — auch bei einem Zweig, den diese Instanz nie genommen hat. Der Text versteht Markdown: Überschriften, Aufzählungen, Code, Fettes, Kursives, Zitate und Links. Tasks-App und Instanz-Replay zeigen ihn gerendert, eine Prüfliste kommt bei der bearbeitenden Person also als Liste an und nicht als Zeile voller Bindestriche. Wer schlicht Text schreibt, bekommt schlicht diesen Text: Zeilenumbrüche bleiben Zeilenumbrüche.

    Every element has a Documentation field in the Details panel — right below its name and id. Put there why the step exists, the rule behind it and who owns it; for the process itself (nothing selected), the summary a reader wants before following the diagram. The text is part of the model: the engine never acts on it, but it survives deploy, export and every version — so the documentation stays with the process instead of going stale in a separate document. On a user task it is more than a note: the Tasks app shows it to the assignee above the form as the work instruction, so write that one to the person who will do the work. The instance replay shows the selected element's documentation under its properties — including for a branch this instance never took. The text understands Markdown: headings, bullet and numbered lists, code, bold, italic, quotes and links. The Tasks app and the instance replay render it, so a checklist reaches the assignee as a list rather than as a line full of hyphens. Write plain prose and you get plain prose: a line break stays a line break.

  6. Prüfen & aufräumenValidate & tidy

    Der Modeler validiert live. Aufgeräumtes Layout ist Teil der Arbeit, nicht Kür.

    The Modeler validates live. A tidy layout is part of the job, not a bonus.

Retries hat jede Aufgabe, die als Job läuft — Service- und Send-Task, jede Worker-Aufgabe (Mail, REST, Jira …), Skript-Task (PowerShell & Co.) und Business-Rule-Task. Im Modeler steht das Feld unter Failure handling; leer bedeutet den Standard 3, 1 heisst „ein Versuch, kein Retry“. Weniger als 1 lehnt der Deploy ab — ein Job ohne Versuch würde nie ausgeliefert.Retries is a property of every task that runs as a job — service and send tasks, every worker task (mail, REST, Jira …), script tasks (PowerShell & co.) and business rule tasks. Variable oder Datenobjekt? Beide können Kunde heissen, und sie sind trotzdem nicht dasselbe. Ein Datenobjekt trägt den deklarierten Typ, einen Datenzustand und die aufgezeichnete Geschichte jedes Schreibvorgangs; eine Variable trägt einen Wert. Sie liegen in getrennten Sätzen und werden von getrennten Ereignissen geschrieben — eine Datenassoziation kopiert, sie wertet ihren Ausdruck einmal aus. Ein Schreibvorgang auf das eine ändert das andere nie. Und nur eines der beiden hört auf den Namen: FEEL wird allein aus den Variablen gebunden, also meint Kunde in einer Bedingung, einem Mapping oder einer Worker-Nutzlast immer die Variable — auch in einem Modell, in dem es um das Objekt geht. Ein Objekt kommt ausschliesslich über eine dataInputAssociation in eine Variable und damit in Reichweite eines Ausdrucks. Deshalb warnt die Problems-Leiste, wenn eine Variable so heisst wie ein Datenobjekt desselben Prozesses (variable.shadows-data-object): Es ist erlaubt, aber die beiden driften unter einem Namen auseinander, während das Diagramm einen Kasten zeigt. Das übliche Muster: Der Task schreibt sein Ergebnis in customer, eine dataOutputAssociation hebt es mit =customer in das Datenobjekt Kunde, und ein späterer Task liest es bei Bedarf in eine anders benannte Variable zurück.Variable or data object? Both can be called Kunde, and they are still not the same thing. A data object carries the declared type, a data state and the recorded history of every write; a variable carries a value. They live in separate records and are written by separate events — a data association copies, evaluating its expression once. Writing one never changes the other. And only one of them answers to the name: FEEL is bound from the variables alone, so Kunde in a condition, a mapping or a worker payload always means the variable, even in a model whose whole point is the object. An object reaches an expression only by way of a dataInputAssociation copying it into a variable. That is why the Problems bar warns when a variable is named after a data object of the same process (variable.shadows-data-object): it is legal, but the two drift apart under one name while the diagram shows one box. The usual pattern: the task writes its result into customer, a dataOutputAssociation lifts it into the data object Kunde with =customer, and a later task reads it back into a differently named variable when it needs one.

That is what data objects are event-sourced for — here a datum has a history, not just a current value.

Worker – Atlas mit der Aussenwelt verbinden

Workers – wiring Atlas to the outside

Ein Service-Task erledigt die Arbeit nicht selbst. Er erzeugt ein Job-Arbeitspaket, Atlas schreibt es dauerhaft weg – und erst danach darf ein Worker es holen und das Fremdsystem anfassen. Diese Reihenfolge ist der Grund, warum ein Ausfall draussen nie einen Fall hier drinnen verliert: Der Token wartet am Job, nicht an einer offenen Verbindung.

A service task does not do the work itself. It creates a job, Atlas stores that job durably – and only then may a worker pick it up and touch the foreign system. That order is why an outage out there never loses a case in here: the token waits at the job, not on an open connection.

Ein Verzeichnis einrichten

Configuring a directory

Ein Active Directory richtest du wie jeden anderen Worker ein: Konsole › Workers → New worker → Worker-Typ Active Directory. Zwei Angaben braucht es: die LDAP-URL des Domain Controllers (ldaps://dc.example.com:636) und eine Credentials-Referenz auf ein Vault-Bündel mit dem Dienstkonto:

You configure an Active Directory the way you configure every other worker: Console › Workers → New worker → worker type Active Directory. It takes two things: the domain controller's LDAP URL (ldaps://dc.example.com:636) and a credential reference naming a vault bundle that holds the service account:

{"bindDN": "cn=svc-atlas,ou=Dienstkonten,dc=example,dc=com", "password": "…"}

Ein Task nennt dann nur noch den Namen des Workers — wo das Verzeichnis steht und wer sich anmeldet, steht nicht mehr im Modell. Das Attribut heisst dabei weiterhin connector (warum):

A task then names the worker and nothing else — where the directory is and who binds to it no longer live in the model. The attribute is still spelled connector (why):

<atlas:adConnector connector="prod-forest" operation="disable" dn="=benutzerDN"/>

Mehrere Verzeichnisse sind mehrere Worker — desselben Worker-Typs. Ein Prozess für den Produktiv-Forest und einer für den Test-Forest nennen einfach unterschiedliche Worker-Namen. Die Jobs beider holt eine AD-Worker-Instanz ab, denn die ist an kein Verzeichnis gebunden. Hier zeigt sich der Unterschied der drei Ebenen am schärfsten: ein zweites Ziel ist ein zweiter Worker, mehr Durchsatz sind mehr Instanzen — und mehr Instanzen trennen nichts, weil Jobs nach Typ verteilt werden und nicht nach Ziel.

Several directories are several workers — of the same worker type. A process for the production forest and one for the test forest simply name different workers. Both their jobs are leased by one AD worker instance, because that instance is bound to no directory. This is where the three levels separate most sharply: a second target is a second worker, more throughput is more instances — and more instances separate nothing, since jobs are handed out by type and not by target.

Verwende ldaps://, sofern du nicht StartTLS aktivierst: Active Directory weigert sich, ein Passwort über eine unverschlüsselte Verbindung zu setzen. Ein ldap://-Verzeichnis funktioniert also für alles ausser für genau das, was ein Joiner am nötigsten braucht.

Use ldaps:// unless you enable StartTLS: Active Directory refuses to set a password over an unencrypted connection. So an ldap:// directory works for everything except the one thing a joiner needs most.

Active Directory ausprobieren, ohne ein Active Directory

Trying Active Directory without an Active Directory

Ein Identity-Prozess ist die eine Sorte, die niemand gefahrlos ausprobieren kann: Das Verzeichnis, in dem er Konten anlegt, ist das echte, und ein Test-Joiner hinterlässt ein echtes Konto. Deshalb kann der Worker, der AD-Aufgaben abarbeitet, gegen ein Verzeichnis in seinem eigenen Arbeitsspeicher laufen.

An identity process is the one kind nobody can safely try out: the directory it creates accounts in is the real one, and a test joiner leaves a real account behind. So the worker that serves AD tasks can run against a directory in its own memory instead.

Am Modell ändert sich dabei nichts – dieselbe Server-URL, derselbe Bind-DN, dieselben Operationen. Anders ist nur, welcher Worker die Aufgaben abholt. Ein Modell, das im Mockup durchläuft, ist also dasselbe Modell, das später produktiv läuft: Der Weg dorthin ist eine Umgebungsvariable, keine Änderung am Prozess.

Nothing changes in the model – the same server URL, the same bind DN, the same operations. What differs is only which worker leases the tasks. A model that runs through in mockup mode is therefore the same model that later runs in production: getting there is an environment variable, not an edit.

Eingeschaltet wird es in der Konsole: Workers → Karte Active Directory → Serve Active Directory tasks against a mockup → Speichern. Die AD-Worker-Instanz startet daraufhin neu und kommt gemockt zurück; Atlas läuft dabei weiter.

Ein Bind-Passwort braucht es trotzdem. Der Mock ist genau dort streng, wo Strengsein der Zweck ist: Ein Simple Bind, der einen DN nennt und kein Passwort schickt, wird abgelehnt – so, wie ein echtes Active Directory ihn ablehnt. Die Token-Referenz, die deine Aufgabe nennt, muss also auch im Mockup auflösbar sein; welchen Wert sie hat, ist dabei völlig egal. Leg sie unter demselben Namen in Workers → Karte Secrets an, oder setze die Variable, die der Incident nennt, in der Umgebung des Workers. Fehlt sie, scheitert die Aufgabe, bevor der Mock überhaupt gefragt wird – der Incident nennt dann die Referenz und die Variable, die ihr fehlt.

Dieselbe Karte nimmt optional einen Startbestand entgegen – die Konten und Gruppen, die dein Prozess vorzufinden erwartet. Ein Joiner braucht keinen, solange er nur sein eigenes Konto anlegt; sobald er es einer Gruppe zuweist, muss diese Gruppe da sein, sonst scheitert er mit no such object. Ein Leaver hat in einem leeren Verzeichnis ohnehin nichts zu deaktivieren. Du wählst eine LDIF- oder DSML-Datei aus oder fügst den Inhalt direkt ein – einen Pfad gibst du nirgends an: Atlas speichert den Bestand selbst und legt ihn dem Worker hin. Beim Speichern wird er geprüft, und Atlas sagt dir, wie viele Einträge er gelesen hat. Wenn dir nichts einfällt, liefert Example ein kleines Verzeichnis mit zwei Konten und einer Gruppe – genug, um einen Leaver auszuprobieren.

You switch it on in the Console: Workers → the Active Directory card → Serve Active Directory tasks against a mockup → Save. The AD worker instance restarts and comes back mocked; Atlas keeps running.

A bind password is still needed. The mockup is strict exactly where being strict is the point: a simple bind that names a DN and sends no password is refused, the way a real Active Directory refuses it. So the token reference your task names has to resolve in mockup mode too; what its value is does not matter in the slightest. Store it under the same name in Workers → the Secrets card, or set the variable the incident names in the worker's environment. Without it the task fails before the mock is ever asked – and the incident names the reference and the variable it is missing.

The same card takes optional starting entries – the accounts and groups your process expects to find. A joiner needs none while it only creates its own account; the moment it adds that account to a group, the group has to be there or it fails with no such object. A leaver has nothing to disable in an empty directory at all. Pick an LDIF or DSML file, or paste the content straight in – there is no path to type: Atlas stores the entries itself and puts them where the worker will find them. They are checked when you save, and Atlas tells you how many entries it read. If nothing comes to mind, Example gives you a small directory with two accounts and a group – enough to try a leaver against.

Einen Worker, den du selbst startest – etwa in einem anderen Netz – erreicht der Schalter nicht. Der liest dieselbe Einstellung aus seiner eigenen Umgebung:

A worker you start yourself – in another network, say – is not reached by the switch. It reads the same setting from its own environment:

ATLAS_AD_MOCK=1 ATLAS_AD_MOCK_SEED=/srv/atlas/forest.ldif atlas worker --connector ad

--connector ad nennt den Worker-Typ, den diese Instanz bedient — nicht einen konfigurierten Worker. Sie bearbeitet damit die Jobs aller AD-Worker, also aller Verzeichnisse.

--connector ad names the worker type this instance serves — not a configured worker. It therefore works the jobs of every AD worker, and so of every directory.

Dort ist der Startbestand wieder ein Pfad, weil dieser Worker auf seinem eigenen Host läuft und Atlas ihm nichts hinlegen kann. Findet er die Datei nicht oder kann sie nicht lesen, startet er mit einem leeren Verzeichnis und schreibt eine Warnung – er verweigert den Start nicht. Ein Joiner merkt davon nichts; ein Leaver scheitert an genau der Stelle, an der das fehlende Konto gebraucht wird, und der Incident zeigt genau dorthin.

There the starting entries are a path again, because that worker runs on its own host and Atlas has nowhere to put them. If it cannot find or read the file it starts with an empty directory and logs a warning – it does not refuse to start. A joiner never notices; a leaver fails exactly where the missing account was needed, and the incident points straight at it.

Zu sehen ist das Ganze unter Betrieb › Workers: Dort läuft der Worker ad. Sein Log warnt beim Start, dass kein Verzeichnis geschrieben wird, und zeigt danach jede simulierte Operation mit ihrem DN – Passwörter sind darin redigiert.

You watch it under Operations › Workers: the worker called ad runs there. Its log warns at startup that no directory is being written, then lists every simulated operation with its DN – passwords redacted.

Das simulierte Verzeichnis selbst steht unter Betrieb › Mock directory: pro Worker eine Karte, pro LDAP-URL ein Baum, und zu jedem Eintrag seine Attribute. Der Worker meldet den Bestand nach jeder Operation an Atlas, deshalb steht dort das Konto, das ein Joiner gerade angelegt hat. Nicht zu verwechseln mit dem Startbestand auf der Karte unter Organisation › Workers: der ist die Vorlage, aus der jedes Verzeichnis beginnt, und wird nie zurückgeschrieben – ein neu angelegtes Konto taucht dort also nicht auf. Beides ist flüchtig: der Worker-Neustart leert seine Verzeichnisse, der Atlas-Neustart die Ansicht.

The simulated directory itself is under Operations › Mock directory: one card per worker, one tree per LDAP URL, and every entry's attributes. The worker reports what it holds after each operation, so the account a joiner just created is there. Do not confuse it with the starting entries on the card under Organization › Workers: those are the template every directory begins from and are never written back, so a newly created account does not appear there. Both are ephemeral: restarting the worker empties its directories, restarting Atlas empties the view.

Mehrere Verzeichnisse bleiben auch im Mockup getrennt. Jede LDAP-URL bekommt ihr eigenes Verzeichnis im Arbeitsspeicher, mit eigenem Bestand und eigener Änderungshistorie. Dasselbe Konto im Produktiv- und im Test-Forest anzulegen gelingt also beidemal — so wie es an zwei echten Domain Controllern gelänge. Der Startbestand ist dabei eine Vorlage: jedes Verzeichnis erhält eine eigene Kopie und entwickelt sich ab dem ersten Schreibzugriff eigenständig weiter.

Several directories stay separate in the mockup too. Each LDAP URL gets its own in-memory directory, with its own entries and its own change history. Creating the same account in the production and the test forest therefore succeeds both times — as it would against two real domain controllers. The starting entries are a template: each directory gets its own copy and goes its own way from the first write.

Der Schalter selbst gilt weiterhin für alle Verzeichnisse zugleich. Das ist Absicht: gleichzeitig eines zu simulieren und in ein anderes wirklich zu schreiben wäre ein Zwischenzustand, dessen ganzes Risiko darin besteht, dass er wie ein vollständiger Mockup-Lauf aussieht.

The switch itself still applies to every directory at once. That is deliberate: simulating one while really writing to another would be a half-state whose whole risk is that it looks like a full mockup run.

Es lehnt ab, was auch AD ablehntIt refuses what AD refuses

Dasselbe Konto ein zweites Mal anlegen, ein Passwort über eine unverschlüsselte Verbindung setzen, ein Gruppenmitglied zweimal hinzufügen, einen Container mit Inhalt löschen, einen Delta-Abgleich an der falschen Stelle im Verzeichnisbaum: Das scheitert im Mockup genauso wie am echten Domain Controller. Genau das ist der Sinn – die Fehler, die man sonst erst in der Produktion trifft, trifft man beim Entwerfen.

Creating the same account twice, setting a password over an unencrypted connection, adding a group member twice, deleting a container that still has children, reading a delta from the wrong place in the tree: all of that fails in the mockup exactly as it does against a real domain controller. That is the point – the mistakes you would otherwise meet in production, you meet while drafting.

Nicht auf einem ProduktivsystemNot on a production system

Ein Mockup-Worker sieht von aussen aus wie ein funktionierender: Er schliesst jede Aufgabe erfolgreich ab. Zwei Stellen verraten den Unterschied – die Karte in der Konsole und die Warnung im Worker-Log. Und das Verzeichnis lebt im Worker-Prozess: ein Neustart beginnt wieder beim Startbestand.

A mockup worker looks exactly like a working one from the outside: it completes every task successfully. Two places give it away – the card in the Console and the warning in the worker's log. And the directory lives in the worker process: a restart starts over from the seed.

Eine Datenbank ausprobieren, ohne eine Datenbank

Trying a database without a database

Bei Datenbanken ist es noch eine Spur unangenehmer als bei Active Directory. Die Datenbank, aus der ein Prozess liest, ist die HR- oder die ERP-Datenbank — genau deshalb ist sie interessant, und genau deshalb will niemand ein Modell im Entwurf darauf loslassen. Ein Worker, der SQL-Aufgaben bedient, kann sie deshalb aus hinterlegten Antworten in seinem eigenen Arbeitsspeicher beantworten.

A database is a shade more awkward than Active Directory. The database a process reads is the HR system or the ERP — which is exactly why it is interesting, and exactly why nobody wants a model under development pointed at it. So a worker that serves SQL tasks can answer them from seeded answers in its own memory instead.

Eingeschaltet wird es in der Konsole: Workers → Karte Databases → Answer database tasks from a mockup → Speichern. Die SQL-Worker-Instanzen starten daraufhin neu und kommen gemockt zurück; Atlas läuft dabei weiter. Ein Schalter gilt für alle drei Produkte — SQL Server zu simulieren und gleichzeitig wirklich nach PostgreSQL zu schreiben sähe aus wie ein vollständiger Mockup-Lauf, und genau danach darf es nie aussehen.

You switch it on in the Console: Workers → the Databases card → Answer database tasks from a mockup → Save. The SQL worker instances restart and come back mocked; Atlas keeps running. One switch covers all three products — simulating SQL Server while really writing to PostgreSQL would look like a full mockup run, which is the one thing it must never look like.

Dieselbe Karte nimmt die hinterlegten Antworten entgegen: Datei auswählen, einfügen oder Example drücken. Einen Pfad gibst du nirgends an — Atlas speichert die Antworten selbst und legt sie dem Worker hin. Beim Speichern werden sie geprüft, und Atlas sagt dir, wie viele Antworten es gelesen hat; ein Tippfehler wird also dort gemeldet, wo du gerade hinsiehst.

The same card takes the prepared answers: choose a file, paste them, or press Example. There is no path to type — Atlas stores the answers itself and puts them where the worker will find them. They are checked when you save, and Atlas tells you how many it read, so a typo is reported where you are looking.

Solange der Mockup läuft, braucht ein Datenbank-Worker in der Konsole keine Verbindungszeichenfolge: Du legst ihn nur mit einem Namen an — den Namen, den dein Task nennt — und er wird bedient. Gibst du trotzdem eine an, bleibt sie im Vault liegen, damit das Ausschalten kein Neutippen ist.

While the mockup is on, a database worker in the Console needs no connection string: create it with a name — the name your task states — and it is served. Give one anyway and it is still sealed into the vault, so turning the mockup off is not a re-typing exercise.

Einen Worker, den du selbst startest – etwa in einem anderen Netz – erreicht der Schalter nicht. Der liest dieselbe Einstellung aus seiner eigenen Umgebung:

A worker you start yourself – in another network, say – is not reached by the switch. It reads the same setting from its own environment:

ATLAS_MSSQL_CONNECTORS=hr-db \
ATLAS_MSSQL_MOCK=1 ATLAS_MSSQL_MOCK_SEED=/srv/atlas/hr-seed.json \
atlas worker --connector mssql

Dort ist der Seed wieder ein Pfad, weil dieser Worker auf seinem eigenen Host läuft und Atlas ihm nichts hinlegen kann. Findet er die Datei nicht, startet er mit einem Mockup ohne Antworten und schreibt eine Warnung — er verweigert den Start nicht. Jede Anweisung scheitert dann und nennt sich selbst, was auf den fehlenden Seed zeigt, statt ihn zu verbergen. ATLAS_MSSQL_CONNECTORS bleibt hier nötig, denn der Task nennt einen Worker beim Namen, und ein Mockup ohne Namen hat nichts, was ein Task ansprechen könnte.

There the seed is a path again, because that worker runs on its own host and Atlas has nowhere to put it. If it cannot find the file it starts with a mockup that has no answers and logs a warning – it does not refuse to start. Every statement then fails naming itself, which points at the missing seed rather than hiding it. ATLAS_MSSQL_CONNECTORS is still required here, because a task names a worker and a mockup with no names has nothing a task could address.

Für die drei Datenbank-Worker-Typen gilt das gleichermassen, mit dem Präfix des jeweiligen Produkts: ATLAS_MARIADB_CONNECTORS, ATLAS_MARIADB_MOCK, ATLAS_MARIADB_MOCK_SEED — und ebenso ATLAS_POSTGRES_…. Es ist derselbe Code: gleiches Mockup, gleiche Startdatei, gleiche Verweigerung bei einer nicht hinterlegten Anweisung, die genau die Variable nennt, die dieser Worker liest. Nur die Platzhalter in der Anweisung gehören dem Produkt: @p1 bei MS SQL, ? bei MariaDB, $1 bei PostgreSQL — und weil die Startdatei Anweisungen wörtlich zuordnet, ist eine Startdatei für MariaDB mit ? geschrieben.

All three database Worker Types work the same way, under their own product's prefix: ATLAS_MARIADB_CONNECTORS, ATLAS_MARIADB_MOCK, ATLAS_MARIADB_MOCK_SEED — and likewise ATLAS_POSTGRES_…. It is the same code: the same mockup, the same seed file, the same refusal of an unseeded statement, naming the exact variable that worker reads. What belongs to the product is the placeholder syntax in the statement — @p1 for MS SQL, ? for MariaDB, $1 for PostgreSQL — and since the seed matches statements literally, a MariaDB seed is written with ?.

Am Modell ändert sich in beiden Fällen nichts: derselbe Worker-Name, dieselbe Anweisung, dieselben Parameter.

In both cases nothing changes in the model: the same worker name, the same statement, the same parameters.

Die Startdatei ordnet Anweisungen ihre Antworten zu. Eine Antwort, die params oder named nennt, gilt nur für genau diese Belegung; eine, die beides weglässt, ist die Auffangantwort derselben Anweisung. So lässt sich „Person 42 gibt es, alle anderen nicht" hinterlegen, ganz ohne SQL-Engine dahinter:

The seed file maps statements to their answers. An answer that names params or named applies only to that binding; one that names neither is the same statement's fallback. That is how a seed can say "person 42 exists and nobody else does", with no SQL engine behind it:

{
  "answers": [
    { "statement": "SELECT id, mail FROM personen WHERE id = @p1",
      "params": [42],
      "columns": ["id", "mail"],
      "rows": [[42, "arno@example.com"]] },

    { "statement": "SELECT id, mail FROM personen WHERE id = @p1",
      "columns": ["id", "mail"], "rows": [] },

    { "statement": "UPDATE personen SET aktiv = 0 WHERE id = @id",
      "named": { "id": 42 }, "affected": 1 },

    { "statement": "INSERT INTO personen (mail) VALUES (@p1)",
      "error": "Violation of UNIQUE KEY constraint 'UQ_personen_mail'" }
  ]
}

Gross-/Kleinschreibung und Zeilenumbrüche sind egal — sonst nichts: Eine andere Spaltenliste ist eine andere Anweisung. Und eine Antwort darf scheitern. Das ist keine Spielerei: Ein doppelt zugestellter Job, der ein zweites Mal einfügt, ist in einem Identity-Prozess kein Sonderfall, sondern der Normalfall der Zustellgarantie — und im Mockup lässt er sich auslösen, wann immer man will.

Case and line breaks do not matter — nothing else is forgiven: a different column list is a different statement. And an answer may fail. That is not a curiosity: a redelivered job that inserts a second time is not an edge case in an identity process, it is what the delivery guarantee routinely does — and in the mockup you can trigger it whenever you like.

Was ein Lauf getan hat, steht unter Betrieb › Mock database: pro Worker eine Karte, darunter jede Anweisung in ihrer Reihenfolge samt der Werte, die der Prozess gebunden hat. Rot sind die ohne hinterlegte Antwort — genau die, die du in die Startdatei übernimmst. Damit schliesst sich die Schleife in der Konsole: Prozess starten, lesen was er gefragt hat, die fehlende Anweisung hinterlegen, nochmal starten.

What a run did is under Operations › Mock database: one card per worker, every statement in order with the values the process bound. The red ones had no prepared answer — exactly the ones you paste into the seed. That closes the loop inside the Console: start the process, read what it asked, add the statement it could not answer, start it again.

Nicht zu verwechseln mit den hinterlegten Antworten auf der Karte unter Organisation › Workers: die sind die Vorlage, aus der der Worker startet, und werden nie zurückgeschrieben. Und es gibt dort keine Tabelle zum Blättern — dieses Mockup beantwortet Anweisungen und führt keine aus, ein INSERT ändert also nicht, was ein späteres SELECT liefert. Beides ist flüchtig: der Worker-Neustart leert sein Journal, der Atlas-Neustart die Ansicht.

Do not confuse it with the prepared answers on the card under Organization › Workers: those are the template the worker starts from and are never written back. And there is no table to browse there — this mockup answers statements and executes none, so an INSERT does not change what a later SELECT returns. Both are ephemeral: restarting the worker empties its journal, restarting Atlas empties the view.

Die Ansicht ist Administratoren vorbehalten, und aus einem strengeren Grund als das Mock-Verzeichnis: Sie zeigt die gebundenen Werte, und ein Prozess bindet, was er bindet — ein Passwort-Hash auf dem Weg in eine Tabelle ist ein gebundener Parameter wie jeder andere, und nichts kann ihn von einer Id unterscheiden.

The view is admin-only, and for a stronger reason than the mock directory: it shows the bound values, and a process binds whatever it binds — a password hash on its way into a table is a bound parameter like any other, and nothing can tell it from an id.

Was nicht hinterlegt ist, scheitertWhat is not seeded, fails

Eine Anweisung ohne hinterlegte Antwort liefert keine leere Trefferliste, sondern lässt die Aufgabe scheitern — mit der Anweisung und den gebundenen Werten im Fehlertext, sodass du sie direkt in die Startdatei übernehmen kannst. Das ist Absicht: „keine Treffer" ist eine fachliche Antwort (die Suche hat niemanden gefunden), und ein Mockup, das sie erfindet, schiebt dem Prozess eine Tatsache unter — in der Richtung, die am schwersten auffällt, weil der Lauf aussieht, als hätte er funktioniert.

A statement with no seeded answer does not come back as an empty result set: it fails the task, with the statement and the bound values in the error so you can paste them straight into the seed. That is deliberate — "no rows" is a business answer (the lookup found nobody), and a mockup that invents one hands the process a fact, in the direction that is hardest to notice, because the run looks like it worked.

Es ist keine DatenbankIt is not a database

Das Mockup beantwortet Anweisungen, es führt sie nicht aus. Ein INSERT ändert also nicht, was ein späteres SELECT liefert — beide sind hinterlegt. Das ist der Preis dafür, keine SQL-Engine zu sein, und der ist bewusst gewählt: Ein Mockup mit SQLite oder einem selbstgebauten SQL-Dialekt wäre genau dort anders als der echte SQL Server, wo Anweisungen schiefgehen — und der Unterschied fiele erst in der Produktion auf. Zum Ausprobieren eines Prozesses taugt es, als Testdatenbank nicht.

The mockup answers statements, it does not execute them. So an INSERT does not change what a later SELECT returns — both are seeded. That is the price of not being a SQL engine, and it is deliberate: a mockup built on SQLite or a hand-written SQL subset would differ from the real SQL Server exactly where statements go wrong, and the difference would surface in production. It is good for trying a process out; it is not a test database.

Empfohlener Test-RhythmusRecommended test rhythm

Simuliere den Fluss → prüfe deine FEEL-Ausdrücke → starte ein paar echte Instanzen mit typischen und untypischen Daten (Grenzwerte, leere Felder, Fehlerfälle) → schau in Operations, ob Timeline und Variablen stimmen. Erst dann produktiv.

Simulate the flow → check your FEEL expressions → start a few real instances with typical and atypical data (boundaries, empty fields, error cases) → check in Operations that the timeline and variables are correct. Only then go to production.

Betrieb & Incidents

Operations & incidents

Im Alltag beobachtest und steuerst du laufende Prozesse in der Operations-App.

Day to day, you watch and steer running processes in the Operations app.

  • Instances – alle Durchläufe, ihr Zustand, Variablen und eine vollständige Timeline jeder Instanz. Eine Version kann hunderttausende Instanzen halten, deshalb zeigt die Liste eine Seite („80 von 150“) und nicht alles: Load more holt die nächste, und das Suchfeld über der Liste findet gezielt eine – gib einen Instanzschlüssel ein (das ist ein einzelner Lesezugriff, egal wie viele Instanzen es gibt) oder name=wert für eine Suche über die Prozessvariablen dieser Version. Damit die Wertsuche ebenfalls ein einzelner Zugriff wird, sagt das Modell, wonach gesucht werden soll: <bpmn:process atlas:searchable="identityId,item">. Für eine so deklarierte Variable beantwortet der Index die Suche; alles andere liest die Instanzen der Version durch. Was du eingibst, wird dabei vollständig verglichen: kdnr=MT-100 findet MT-100 und nicht MT-10001. Erweitern tust du selbst – * steht für beliebig viele Zeichen, ? für genau eines, also findet *MT-1* alles, worin MT-1 vorkommt. Willst du nach einem echten Stern oder Fragezeichen suchen, schreibe \* oder \?. Ein Prozess, der nichts deklariert, zahlt dafür nichts.
  • Instances – all runs, their state, variables and a complete timeline per instance. A version can hold hundreds of thousands of instances, so the list shows a page ("80 of 150") rather than everything: Load more fetches the next one, and the search box above the list finds a specific one – type an instance key (one read, whatever the instance count) or name=value to search this version's process variables. To make the value search one read too, the model says what it wants to be found by: <bpmn:process atlas:searchable="identityId,item">. For a variable declared that way the index answers the search; anything else reads through the version's instances. Either way what you type is matched whole: kdnr=MT-100 finds MT-100 and not MT-10001. Widening is yours to ask for – * stands for any run of characters and ? for exactly one, so *MT-1* finds anything containing MT-1. To search for a real star or question mark, write \* or \?. A process that declares nothing pays nothing for it.
  • Incidents – wenn ein Token nicht weiterkommt (Job fehlgeschlagen, Ausdrucksfehler, fehlende Variable), entsteht ein Incident. Du behebst die Ursache und löst ihn auf – die Instanz läuft weiter. Du musst dafür nicht in die Liste: das steckengebliebene Element ist in der Live-Ansicht und im Replay rot markiert und mit ⚠ beschriftet, die Meldung steht neben dem Diagramm, und Auflösen ist genau dort ein Klick. In der Live-Ansicht zeigt „All instances“ alle steckengebliebenen Instanzen einer Version auf einmal, und die Instances-Liste hat eine Spalte Incidents, die direkt auf die betroffene Version führt. Der Zähler am Navigationspunkt Incidents sagt dir schon vorher, dass überhaupt etwas feststeckt.
  • Incidents – when a token can't proceed (job failed, expression error, missing variable), an incident is raised. You fix the cause and resolve it – the instance resumes. You don't have to go to the list for that: the stuck element is marked red and badged ⚠ in the live view and in the replay, the message sits beside the diagram, and Resolve is one click right there. In the live view, "All instances" shows every stuck instance of a version at once, and the Instances list has an Incidents column that opens the affected version. The count on the Incidents nav entry tells you something is stuck before you open anything.
  • Decisions – jede ausgewertete DMN-Entscheidung mit Ein- und Ausgaben.
  • Decisions – every evaluated DMN decision with its inputs and outputs.
  • Workers – die laufenden Worker-Instanzen: welcher Prozess welche Job-Typen bedient, wie viel gerade wartet, was er zuletzt erledigt hat. Hier steht die Laufzeit – was konfiguriert ist, steht in Console → Workers.
  • Workers – the running worker instances: which process serves which job types, how much is waiting right now, what it settled last. This is the runtime side – what is configured lives in Console → Workers.
MerkeRemember

Ein Incident ist kein Datenverlust – die Instanz pausiert sicher an genau der Stelle. Nichts geht verloren, während du recherchierst.

An incident is not data loss – the instance pauses safely at exactly that spot. Nothing is lost while you investigate.

Atlas installieren & betreiben

Installing & operating Atlas

Atlas ist ein einziges, in sich geschlossenes Binary – keine Datenbank, kein Broker, keine Laufzeit-Abhängigkeiten. Engine, HTTP-API und diese ganze Oberfläche stecken darin. Herunterladen, Prüfsumme verifizieren, starten.

Atlas is one self-contained binary – no database, no broker, no runtime dependencies. The engine, the HTTP API and this entire UI are compiled into it. Download it, verify the checksum, run it.

  • Genau ein Prozess pro Datenverzeichnis. Atlas ist eine Single-Writer-Engine – zwei Server auf demselben Verzeichnis beschädigen es.
  • Exactly one process per data directory. Atlas is a single-writer engine – two servers on the same directory will corrupt it.
  • Nichts erreicht Atlas im Klartext. Entweder terminiert Atlas TLS selbst – --tls-cert und --tls-key machen aus dem Port einen TLS-1.3-Listener, beide Dateien oder keine – oder ein Reverse Proxy davor tut es. Eins von beidem, bevor jemand von aussen darauf zugreifen kann. Verschlüsselung ist keine Autorisierung: /metrics, /healthz und /readyz antworten jedem, der den Port erreicht.
  • Nothing should reach Atlas in the clear. Either Atlas terminates TLS itself – --tls-cert and --tls-key turn the port into a TLS 1.3 listener, both files or neither – or a reverse proxy in front of it does. One of the two, before anyone outside the host can reach it. Encryption is not authorization: /metrics, /healthz and /readyz answer whoever can reach the port.
  • Sichere den Vault-Key. Ein Datenverzeichnis ohne seinen vault.key ist nicht wiederherstellbar – die darin gespeicherten Worker-Secrets sind dann nicht mehr lesbar.
  • Back up the vault key. A data directory without its vault.key is not recoverable – the workers' secrets in it can no longer be read.

Konten, Rollen & Anmeldung

Accounts, roles & sign-in

Wer sich anmelden kann – und was er danach darf. Beides wird unter Console → Organization verwaltet.

Who can sign in – and what they may do afterwards. Both are managed under Console → Organization.

Die vier Rollen

The four roles

Jeder Endpunkt nennt die Rolle, die ihn erreicht, und der Server prüft sie, bevor die Anfrage irgendetwas anderes berührt – gleich, ob sie aus dem Browser kommt, mit einem API-Token oder über MCP von einem KI-Assistenten.

Every endpoint names the role that reaches it, and the server checks it before the request touches anything else – whether it arrives from a browser, with an API token, or over MCP from an AI assistant.

RolleRole Was sie öffnetWhat it opens
admin Konten, Gruppen, Zugangsdaten, Secrets, Einstellungen, Backup und Restore – alles, was die Installation selbst betrifft. Accounts, groups, credentials, secrets, settings, backup and restore – everything about the instance itself.
modeler Entwürfe, Formulare, Entscheidungen und Worker bearbeiten – und deployen. Deployen ist Codeausführung, deshalb ist es genau diese Rolle und nicht «angemeldet». Editing drafts, forms, decisions and workers – and deploying. Deploying is code execution, which is why it takes this role rather than merely being signed in.
operator Instanzen starten, abbrechen und reparieren, Incidents auflösen, Workers und Outbox – der Betrieb dessen, was deployt ist. Starting, cancelling and repairing instances, resolving incidents, workers and the outbox – running what is deployed.
user Die eigene Aufgabenliste: Aufgaben sehen, übernehmen und abschliessen. Their own task list: seeing, claiming and completing tasks.
  • Eine Liste, keine Rangfolge. Ein Konto trägt mehrere Rollen; modeler enthält operator nicht. Nur admin ist eine Obermenge und erreicht alles.
  • A list, not a ladder. An account carries several roles; modeler does not contain operator. Only admin is a superset and reaches everything.
  • Neue Konten bekommen user – und sonst nichts. Den Rest vergibt eine Administratorin bewusst.
  • New accounts get user – and nothing else. An administrator grants the rest deliberately.
  • Die Rollenprüfung gilt auch für Token und KI-Assistenten: Ein MCP-Werkzeug läuft mit den Rollen dessen, der es ruft, und kann nichts, was diese Person nicht auch von Hand könnte.
  • The check applies to tokens and AI assistants too: an MCP tool runs as its caller and can do nothing that person could not do by hand.

Gruppen

Groups

Eine Gruppe ist eine benannte Menge von Konten. Sie ist die zweite Achse neben den Rollen: Rollen sagen, welche Art von Endpunkt jemand erreicht, eine Freigabe an eine Gruppe sagt, welches Objekt – ein Projekt oder ein Worker wird einmal mit dem Team geteilt statt Person für Person. Eine Änderung an der Mitgliedschaft wirkt bei der nächsten Anmeldung des Mitglieds.

A group is a named set of accounts. It is the second axis beside roles: a role says which kind of endpoint somebody reaches, sharing with a group says which object – a project or a worker is shared with the team once instead of person by person. A membership change takes effect at the member's next sign-in.

Wer gerade angemeldet ist

Who is signed in right now

Die Benutzerliste hat neben Status – darf sich anmelden – eine Spalte Presence: Ist gerade jemand da. Online heisst, in den letzten fünf Minuten hat diese Person etwas getan; idle, dass ihre Sitzung offen, aber unberührt ist; offline, dass für das Konto kein Browser mehr meldet – auch dann, wenn seine Sitzung technisch noch Stunden gültig wäre, denn ein zugeklappter Laptop meldet sich nicht ab. Der Browser meldet dafür einmal pro Minute zweierlei getrennt: dass der Tab offen ist, und ob ihn jemand angefasst hat. Ohne diese Trennung wäre jeder Tab hinter einem anderen Fenster für immer «online», denn die Konsole fragt von sich aus nach.

Beside Status – may this account sign in – the user list carries a Presence column: is anybody there. Online means this person did something in the last five minutes; idle that their session is open but untouched; offline that no browser is reporting for the account – including when its session would technically be valid for hours yet, because a laptop that is closed does not log out. The browser reports two separate things once a minute for this: that the tab is open, and whether anybody touched it. Without that separation every tab parked behind another window would read "online" forever, because the Console polls on its own.

Gespeichert wird nichts davon. Die Anwesenheit wird aus den laufenden Sitzungen gelesen und aus nichts sonst: kein Datensatz, kein Ereignis, nichts in der Sicherung, und nach einem Neustart zeigt sie niemanden – nach einem Neustart ist auch niemand angemeldet. Sie ist bewusst grob (drei Zustände, nie welche Seite oder welche Aktion) und nur für admin sichtbar. Eine Anwesenheitshistorie ist es ausdrücklich nicht; wer sich wann angemeldet hat, steht im Audit-Log.

None of it is stored. Presence is read from the live sessions and from nothing else: no record, no event, nothing in a backup, and after a restart it shows nobody – after a restart nobody is signed in either. It is deliberately coarse (three states, never which page or which action) and visible to admin only. It is explicitly not an attendance history; who signed in when is in the audit log.

Anmelden mit einem Identitätsanbieter

Signing in with an identity provider

Optional, und aus, solange niemand einen Anbieter konfiguriert. Ist einer eingerichtet, trägt die Anmeldemaske zusätzlich eine Schaltfläche «Sign in with …»: Die Person authentisiert sich dort, wo sie es ohnehin tut, und kommt angemeldet zurück. Zweitfaktor und Passwortregeln werden damit zur Sache des Anbieters, und ein dort geschlossenes Konto kommt hier nicht mehr hinein. Informationsmodell: was die Daten sind

Information model: what the data is

Ein Datenobjekt im Prozess ist ein echtes, typisiertes Ding mit Wert und Historie – aber nur innerhalb einer Prozessdefinition. Zwei Prozesse, die beide einen auftrag führen, führen zwei völlig unabhängige Dinge, und nichts sagt irgendwo, dass dasselbe gemeint ist. Die App Data schliesst genau diese Lücke.

A data object in a process is a real, typed thing with a value and a history – but only inside one process definition. Two processes that both carry an order carry two entirely unrelated things, and nothing anywhere states that they mean the same one. The Data app closes exactly that gap.

Warum BPMN hier aufhört

Where BPMN stops

Das ist keine Lücke in Atlas, sondern eine Eigenschaft des Standards:

This is not a gap in Atlas but a property of the standard:

  • Ein dataObject gehört der Prozessdefinition, die es deklariert. Sein Name ist eine Zeichenkette, die nur dort gilt.
  • A dataObject belongs to the process definition that declares it. Its name is a string local to that definition.
  • BPMNs Typ-Steckplatz itemSubjectRef zeigt absichtlich in eine andere Sprache – der Standard lässt offen, wohin. Ohne ein Gegenüber ist er eine Zeichenkette ohne Bedeutung.
  • BPMN's type slot itemSubjectRef deliberately points into some other schema language – the specification leaves the target open. With nothing on the other side it is a string without meaning.
  • Die Frage «welche Prozesse fassen denselben Auftrag an?» hat damit schlicht keine Antwort. Und das ist die Frage, die zählt, sobald es mehr als einen Prozess gibt.
  • So the question "which processes touch the same order?" has no answer at all. And that is the question that matters as soon as there is more than one process.

Die Antwort der OMG auf diese Frage war immer «das gehört in einen anderen Standard», und dieser andere Standard ist UML. Deshalb ist das Informationsmodell ein UML-Klassendiagramm.

The OMG's own answer has always been "that belongs to another standard", and that other standard is UML. Which is why the information model is a UML class diagram.

Was ein Modell enthält

What a model holds

Ein Informationsmodell gehört einer Applikation und gilt für alle ihre Prozesse. Es beschreibt Begriffe, keine Tabellen – wo ein Datum tatsächlich gespeichert wird, ist eine andere Frage und wird pro Speicher entschieden.

  • Klassen mit ihren Attributen, Typen und Kardinalitäten.
  • Classes with their attributes, types and multiplicities.
  • Beziehungen zwischen ihnen.
  • Relationships between them.
  • Der Business Key – siehe unten. Das ist der Teil, auf den es ankommt.
  • The business key – see below. That is the part that matters.

Welche Klassenarten es gibt, welche Beziehung zwischen welchen laufen darf und welche primitiven Typen zur Verfügung stehen, liefert der Server; die Zeichenfläche hält keine eigene Kopie davon. Zwei Kopien einer Regelmatrix wären der Weg zu einer Leinwand, die einen Pfeil zeichnen lässt, den der Server anschliessend ablehnt.

Which class kinds exist, which relationship may run between which of them and which primitive types are available all come from the server; the canvas keeps no copy. Two copies of a rule matrix is how you get a canvas that lets somebody draw an arrow the server then rejects.

Der Business Key

The business key

Der Business Key ist die eine Angabe, für die BPMN kein Gegenstück hat: die Tatsache, die sagt, dass zwei Dinge dasselbe Ding sind. Bei einem Auftrag ist das die Auftragsnummer, bei einer Bewerbung die Referenz, bei einer Person die Sozialversicherungsnummer – was immer im Fachbereich als Identität gilt.

The business key is the one fact BPMN has no equivalent for: the fact that says two things are the same thing. For an order it is the order number, for an application the reference, for a person a social security number – whatever counts as identity in the business.

Wenn du nur eine Sache modellierst
If you model only one thing

Dann den Business Key. Klassennamen kann jeder rekonstruieren; der Schlüssel ist die Angabe, die beim Abtippen eines fremden Modells als Erstes verlorengeht – und ohne ihn lässt sich nicht sagen, ob der Auftrag in Prozess A und der in Prozess B derselbe ist.

Then the business key. Class names anybody can reconstruct; the key is the fact that goes missing first when somebody retypes a foreign model – and without it there is no way to say whether the order in process A and the one in process B are the same one.

Zwei Eigenschaften des Imports sind wichtiger als die Formatliste:

Two properties of the import matter more than the list of formats:

  • Er sagt, was verlorengeht – Element für Element. Ein Import, der seine Verluste verschweigt, ist schlimmer als kein Import, weil die Lücke erst auffällt, wenn ein Deploy gegen eine Klasse auflöst, die still ihren Schlüssel verloren hat.

Der Arbeitszyklus

The working cycle

  1. Fachlichkeit klärenClarify the domain

    Wer löst einen Fall aus, wer arbeitet daran, wie viele sind es am Tag, wie lange darf er dauern – und was darf schiefgehen. Die letzte Frage wird am häufigsten vergessen und bestimmt am meisten am Modell.

    Who triggers a case, who works on it, how many per day, how long may it take – and what is allowed to go wrong. The last question is the one most often skipped, and the one that shapes the model most.

  2. Den Fall schneidenCut the case

    Was ist eine Instanz? Eine Bewerbung, eine Bestellung, ein Gerät – nicht „der Bewerbungsprozess“. Und: welcher Teil taucht so oft auf, dass er ein eigener, aufrufbarer Prozess sein sollte?

    What is one instance? One application, one order, one device – not "the hiring process". And: which part recurs often enough to become its own callable process?

  3. Den Datenvertrag festlegenFix the data contract

    Welche Variablen trägt eine Instanz, wer schreibt sie, wer liest sie. Schreib sie auf, bevor du modellierst – sonst schreibt das Modell sie für dich, und zwar dreimal verschieden.

    Which variables an instance carries, who writes them, who reads them. Write them down before you model – otherwise the model writes them for you, three different ways.

  4. Den Happy Path modellierenModel the happy path

    Eine gerade Linie, fünf bis neun Schritte. Wenn der Weg ohne Zwischenfälle nicht auf eine Achse passt, ist der Fall zu gross geschnitten.

    One straight line, five to nine steps. If the uneventful path does not fit on one axis, the case is cut too big.

  5. Abweichungen ergänzenAdd the deviations

    Fristen, Rückfragen, Abbrüche, ausgefallene Umsysteme. Jede Abweichung bekommt einen sichtbaren Weg im Diagramm – nicht eine Bedingung mehr in einem Gateway.

    Deadlines, queries, cancellations, systems that are down. Every deviation gets a visible path on the diagram – not one more condition inside a gateway.

  6. Umsysteme erst simulierenSimulate the systems first

    Ein Service-Task im Mockup-Modus antwortet mit Verzögerung, Ergebnis und Ausfallquote – du kannst den ganzen Ablauf durchspielen, bevor irgendeine echte Schnittstelle existiert. Die Anbindung ersetzt später genau dieses eine Element.

    A service task in mockup mode answers with a delay, a result and a failure rate – you can play the whole flow through before any real interface exists. The real connection later replaces exactly that one element.

  7. Durchspielen und testenPlay it through and test

    Erst simulieren, dann echte Instanzen mit typischen und untypischen Daten. Grenzwerte, leere Felder, der Fall, der zurückgezogen wird.

    First simulate, then real instances with typical and atypical data. Boundaries, empty fields, the case that gets withdrawn.

  8. Publizieren, betreiben, weiterentwickelnPublish, operate, evolve

    Die Applikation als Ganzes publizieren, in Operations zusehen, die nächste Version bauen – und wissen, dass laufende Instanzen ihre Version behalten, bis du sie migrierst.

    Publish the application as a whole, watch it in Operations, build the next version – knowing that running instances keep their version until you migrate them.

Handwerksregeln

Rules of the craft

  • Benenne im Imperativ.Name in the imperative. „Vertrag anlegen“, nicht „Vertragsanlage“. Ein Task ist eine Handlung; ein Ereignis ist ein Zustand („Bewerbung eingegangen“). "Create the contract", not "Contract creation". A task is an action; an event is a state ("Application received").
  • Das Diagramm ist kein Programm.The diagram is not a program. Wenn du anfängst, Gateways zu verschachteln, ist die Regel eine Entscheidung und gehört in eine Tabelle. The moment you start nesting gateways, the rule is a decision and belongs in a table.
  • Variablen sind eine öffentliche Schnittstelle.Variables are a public interface. Formulare, Skripte, Entscheidungen und Worker lesen dieselben Namen. Benenne sie einmal richtig; ein Zielname ist immer eine Variable, nie ein Pfad mit Punkt. Forms, scripts, decisions and workers read the same names. Get them right once; a write target is always a variable, never a dotted path.
  • Jeder Fall bekommt eine Antwort.Every case gets an answer. Ein Default-Zweig, der ins Leere läuft, ist ein Kunde, der nie wieder von dir hört. A default branch that goes nowhere is a customer who never hears from you again.
  • Fehler sind Fachlichkeit.Failure is part of the domain. „Umsystem nicht erreichbar“ ist ein Weg im Modell, kein Incident. Ein Incident ist, was du nicht vorhergesehen hast. "System unreachable" is a path in the model, not an incident. An incident is what you did not foresee.
  • Dokumentiere im Modell.Document inside the model. Das Dokumentationsfeld reist mit jedem Deploy, Export und jeder Version mit; ein Kommentar im Chat nicht. An einer User-Task ist es die Arbeitsanweisung, die im Posteingang über dem Formular steht. The documentation field travels with every deploy, export and version; a comment in a chat does not. On a user task it is the work instruction shown above the form in the inbox.
  • Zeit ist ein Ereignis, kein Warten.Time is an event, not waiting. Eine Frist ist ein Timer im Modell – sichtbar, durabel, im Replay nachvollziehbar. Kein sleep in einem Skript. A deadline is a timer in the model – visible, durable, replayable. Never a sleep in a script.
  • Rechne mit dem zweiten Versuch.Expect the second attempt. Ein Schritt, der ein Umsystem verändert, kann wiederholt werden. Gib ihm einen fachlichen Schlüssel mit, damit zweimal ausführen nicht zweimal buchen heisst. A step that changes a foreign system can be retried. Give it a business key so running twice does not mean booking twice.
Definition of DoneDefinition of done

Ein Prozess ist fertig, wenn: jeder Zweig endet · jeder menschliche Schritt ein Formular und eine Arbeitsanweisung hat · jedes Umsystem einen Ausfallweg hat · jede Frist im Modell steht · das Diagramm auf einer Achse lesbar ist · die Variablen benannt und dokumentiert sind · du ihn mit untypischen Daten laufen lassen hast und in Operations nachvollziehen konntest, warum er den Weg genommen hat, den er genommen hat.

A process is done when: every branch ends · every human step has a form and a work instruction · every foreign system has a failure path · every deadline is in the model · the diagram reads along one axis · the variables are named and documented · you have run it with atypical data and could tell from Operations why it took the path it took.

Der FallThe case

Eine Bewerbung geht ein. Sie wird bestätigt und vorgeprüft; je nach Abschluss und Erfahrung folgen eine oder zwei Interviewrunden. Danach entscheidet HR über die Einstellung; bei einer Zusage wird der Vertrag im HR-System angelegt. Eine Bewerbung kann jederzeit zurückgezogen werden, HR kann eine Entscheidung liegen lassen, und das HR-System fällt gelegentlich aus. Alle vier Sätze stehen am Ende im Modell.

An application arrives. It is acknowledged and pre-screened; depending on degree and experience, one or two interview rounds follow. HR then decides on hiring; on a yes the contract is created in the HR system. An applicant can withdraw at any time, HR can leave a decision sitting, and the HR system goes down now and then. All four sentences end up in the model.

In zehn Schritten gebaut

Built in ten steps

  1. Die Applikation anlegenCreate the application

    Zuerst die Klammer, dann der Inhalt: eine Applikation ist das, was gemeinsam publiziert, versioniert und exportiert wird. Jedes Artefakt, das du danach anlegst, gehört ihr – ein Formular ohne Applikation findet beim Publizieren niemand.

    The bracket first, the content second: an application is what gets published, versioned and exported as one. Every artifact you create afterwards belongs to it – a form without an application is one nobody finds at publish time.

  2. Das Start-Formular ist der DatenvertragThe start form is the data contract

    Was hier nicht erfasst wird, existiert im Prozess nicht. Zwei Felder verdienen einen zweiten Blick: abschluss und erfahrungJahre sind die Eingaben der DMN-Entscheidung, und email wird später der Korrelationsschlüssel für den Rückzug. Namen also nicht nach Gefühl vergeben – drei andere Artefakte lesen sie.

    What is not captured here does not exist in the process. Two fields deserve a second look: abschluss and erfahrungJahre are the DMN decision's inputs, and email later becomes the correlation key for the withdrawal. So do not name them by feel – three other artifacts read them.

    { "key": "abschluss", "type": "select", "label": "Höchster Abschluss",
  "values": [ { "label": "Master", "value": "master" }, … ] }
  3. Die Regel in eine TabelleThe rule into a table

    „Master mit fünf Jahren: zwei Runden; Studium mit zwei Jahren: eine Runde; Lehre mit fünf: eine Runde; sonst Absage“ – als Gateway-Kaskade wäre das vier verschachtelte Rauten. Als DMN-Tabelle ist es vier Zeilen, die HR selbst pflegen kann. Der Clou steht in der zweiten Ausgabespalte: runden ist eine Liste, keine Zahl.

    "Master with five years: two rounds; a degree with two years: one round; apprenticeship with five: one round; otherwise reject" – as a gateway cascade that is four nested diamonds. As a DMN table it is four rows HR can maintain. The trick is in the second output column: runden is a list, not a number.

    abschluss (in)erfahrungJahre (in)empfehlung (out)runden (out)
    "master">= 5"interview"["Fachinterview", "Führungsinterview"]
    "master", "bachelor">= 2"interview"["Fachinterview"]
    "lehre">= 5"interview"["Fachinterview"]
    ––"absage"[]

    Hit-Policy FIRST: die Regeln dürfen sich überlappen, die erste passende gewinnt, und die letzte Zeile fängt alles auf – kein Fall bleibt ohne Antwort. Der Business-Rule-Task ruft die Tabelle auf und legt das Ergebnis in einer Variablen ab:

    Hit policy FIRST: rules may overlap, the first match wins, and the last row catches everything – no case is left without an answer. The business rule task calls the table and puts the result in a variable:

    <businessRuleTask id="pruefung" name="Vorprüfung">
  <extensionElements>
    <zeebe:calledDecision decisionId="bw-vorpruefung" resultVariable="pruefung"/>
    <zeebe:ioMapping>
      <zeebe:input source="=abschluss" target="abschluss"/>
      <zeebe:input source="=erfahrungJahre" target="erfahrungJahre"/>
    </zeebe:ioMapping>
  </extensionElements>
</businessRuleTask>

    pruefung enthält danach { empfehlung: "interview", runden: ["Fachinterview", "Führungsinterview"] }.

    pruefung then holds { empfehlung: "interview", runden: ["Fachinterview", "Führungsinterview"] }.

    StolpersteinGotcha

    Atlas löst eine Entscheidung über ihren Namen auf. Halte id und name der <decision> identisch, sonst findet der Deploy sie nicht und weist die ganze Applikation zurück.

    Atlas resolves a decision by its name. Keep the <decision>'s id and name identical, otherwise the deploy cannot find it and refuses the whole application.

  4. Auf das Ergebnis verzweigenBranch on the result

    Das Gateway entscheidet nichts mehr – es liest nur, was die Tabelle entschieden hat. Der Default-Zweig führt zur Absage: was nicht ausdrücklich eingeladen wird, wird abgesagt.

    The gateway decides nothing any more – it only reads what the table decided. The default flow leads to the rejection: whatever is not explicitly invited gets a rejection.

    <sequenceFlow id="f_gw_interviews" name="einladen"
              sourceRef="gw_pruefung" targetRef="interviews">
  <conditionExpression>= pruefung.empfehlung = "interview"</conditionExpression>
</sequenceFlow>
  5. Zerlegen: das Interview wird ein eigener ProzessDecompose: the interview becomes its own process

    Eine Interviewrunde ist ein Ablauf für sich: Termin, Gespräch, Feedback, Frist. Sie kommt mehrfach vor. Also wird sie ein eigenständig deployter Prozess (bw-interview), den eine Call-Activity aufruft – einzeln testbar, einzeln versionierbar, später auch von anderen Prozessen nutzbar.

    One interview round is a flow in itself: schedule, conversation, feedback, deadline. It occurs more than once. So it becomes a separately deployed process (bw-interview) that a call activity calls – testable on its own, versionable on its own, usable by other processes later.

    Der Aufruf ist ein Vertrag, kein gemeinsamer Datentopf. Beide propagateAll…-Flags stehen auf false, und die ioMapping sagt genau, was rein- und was rausgeht:

    The call is a contract, not a shared bucket of data. Both propagateAll… flags are false, and the ioMapping states exactly what goes in and what comes out:

    <zeebe:calledElement processId="bw-interview"
    propagateAllParentVariables="false" propagateAllChildVariables="false"/>
<zeebe:ioMapping>
  <zeebe:input  source="=name"   target="name"/>
  <zeebe:input  source="=stelle" target="stelle"/>
  <zeebe:input  source="=runde"  target="runde"/>
  <zeebe:output source="=bewertung" target="bewertung"/>
</zeebe:ioMapping>

    Ohne diese Flags erbt der Teilprozess alles, was der Fall gerade mit sich trägt, und gibt alles zurück. Das funktioniert – bis jemand im Teilprozess eine Variable umbenennt und der Aufrufer stillschweigend kaputtgeht.

    Without those flags the child inherits everything the case happens to carry and hands everything back. That works – until someone renames a variable in the child and the caller breaks silently.

  6. Wiederholen: einmal je RundeRepeat: once per round

    Wie oft der Teilprozess läuft, hat die DMN-Tabelle entschieden. Die Multi-Instance iteriert über pruefung.runden, seriell – die zweite Runde ergibt erst nach dem Feedback der ersten Sinn – und sammelt jede Rückgabe in bewertungen:

    How often the child runs was decided by the DMN table. The multi-instance iterates over pruefung.runden, sequentially – a second round only makes sense after the first one's feedback – and collects each return value into bewertungen:

    <multiInstanceLoopCharacteristics isSequential="true">
  <extensionElements>
    <zeebe:loopCharacteristics inputCollection="=pruefung.runden" inputElement="runde"
        outputCollection="bewertungen" outputElement="=bewertung"/>
  </extensionElements>
</multiInstanceLoopCharacteristics>

    Eine dritte Runde einzuführen heisst jetzt: eine Zeile in der Tabelle ändern. Das Modell bleibt, wie es ist. Genau dafür trennt man Regel und Ablauf.

    Introducing a third round now means: change one row in the table. The model stays as it is. That separation of rule and flow is the whole point.

    Der Vertrag gilt auf jedem WegThe contract holds on every path

    Der Teilprozess hat zwei Enden: Feedback erfasst – oder Frist abgelaufen. Beide schreiben eine bewertung; das Fristende schreibt eine mit „nein“ und einer Notiz. Fände die Sammelstelle beim Zusammenführen nichts vor, hätte die Liste ein Loch – und die Auswertung rächte sich einen Schritt später.

    The child has two ends: feedback captured – or deadline expired. Both write a bewertung; the deadline writes one with "no" and a note. If the collector found nothing there, the list would have a hole – and the evaluation one step later would pay for it.

  7. Verdichten, damit ein Mensch entscheiden kannCondense it so a human can decide

    Eine Liste von Objekten ist keine Entscheidungsgrundlage. Ein Inline-Script macht daraus einen Satz – erst das Urteil über alle Runden, dann jede Runde einzeln:

    A list of objects is not something to decide on. An inline script turns it into one sentence – first the verdict over all rounds, then each round:

    = (if every b in bewertungen satisfies b.empfehlung = "ja"
     then "Alle Runden empfehlen: ja" else "Nicht alle Runden empfehlen")
  + " — "
  + string join(for b in bewertungen
                return b.runde + ": " + b.empfehlung + " (" + b.notiz + ")", " | ")

    Das Ergebnis steht im Formular der Aufgabe Einstellung entscheiden. Und weil ein Mensch eine Aufgabe auch mal liegen lässt, hängt ein nicht unterbrechender Boundary-Timer (P3D) daran, der nebenher eine Erinnerung auslöst, ohne die Aufgabe abzubrechen. Eine unterbrechende Frist wäre hier fachlich falsch: eine Bewerbung darf nicht verfallen, sie soll nur nicht liegen bleiben.

    The result shows up in the form of the decide on hiring task. And because a human does leave a task sitting, a non-interrupting boundary timer (P3D) hangs on it, firing a reminder alongside without cancelling the task. An interrupting deadline would be wrong here: an application must not expire, it should just not be forgotten.

  8. Umsysteme: erst simulieren, dann anbindenForeign systems: simulate first, connect later

    Vier Schritte reden mit der Aussenwelt: Eingangsbestätigung, Erinnerung, Absage und „Vertrag im HR-System anlegen“. Keiner davon braucht für dieses Kapitel eine echte Anbindung – sie laufen im Mockup-Modus, in dem die Engine das Umsystem selbst simuliert: mit Antwortzeit, geskripteter Antwort und Ausfallquote.

    Four steps talk to the outside world: acknowledgement, reminder, rejection and "create the contract in the HR system". None of them needs a real connection for this chapter – they run in mockup mode, where the engine simulates the system itself: response time, scripted answer, failure rate.

    <atlas:mockupConnector minDuration="PT1S" maxDuration="PT4S"
    resultExpression="={ vertragsnummer: &quot;V-2026-0815&quot; }"
    resultVariable="vertrag"
    failRate="0.2" errorCode="HR_UNERREICHBAR"/>

    So läuft die Applikation end-to-end, bevor eine einzige Schnittstelle existiert – und der Fachbereich sieht den echten Ablauf statt eines Foliensatzes. Steht die REST- oder Mail-Anbindung später, ersetzt sie genau dieses eine Element; der Rest des Modells bleibt unberührt.

    That makes the application run end to end before a single interface exists – and the business sees the real flow instead of a slide deck. When the REST or mail connection arrives later, it replaces exactly that one element; the rest of the model is untouched.

  9. Wenn das Umsystem ausfälltWhen the system is down

    Die failRate von 0.2 ist kein Gag: in etwa jedem fünften Lauf wirft „Vertrag im HR-System anlegen“ den Fehler HR_UNERREICHBAR. Eine Error-Boundary fängt ihn und macht daraus eine Aufgabe für einen Menschen – „Vertrag manuell anlegen“.

    The failRate of 0.2 is not a joke: in roughly every fifth run "create the contract in the HR system" throws HR_UNERREICHBAR. An error boundary catches it and turns it into a task for a human – "create the contract by hand".

    Das ist der Unterschied zwischen einem modellierten Fehlerweg und einem Incident: der Fall ist nicht steckengeblieben, er ist zugewiesen. Ein Incident bleibt das, was du nicht vorhergesehen hast – und dafür ist Operations da.

    That is the difference between a modelled failure path and an incident: the case is not stuck, it is assigned. An incident stays what you did not foresee – and that is what Operations is for.

  10. Was jederzeit passieren kannWhat can happen at any time

    Ein Rückzug hängt an keinem Schritt – er kann vor der Vorprüfung kommen, zwischen zwei Interviews, nach der Zusage. Genau dafür gibt es den Event-Subprozess: er hängt am ganzen Prozess. Sein Start ist unterbrechend, beendet den Fall also und räumt eine offene Interview-Aufgabe aus dem Posteingang.

    A withdrawal hangs on no step – it can arrive before the screening, between two interviews, after the offer. That is exactly what an event subprocess is for: it hangs on the whole process. Its start is interrupting, so it ends the case and clears an open interview task out of the inbox.

    <message id="msg_rueckzug" name="bw-rueckzug">
  <extensionElements><zeebe:subscription correlationKey="=email"/></extensionElements>
</message>

    Der Korrelationsschlüssel ist die E-Mail-Adresse aus dem Start-Formular – deshalb war Schritt 2 wichtiger, als er aussah. Auslösen lässt sich die Nachricht von aussen:

    The correlation key is the e-mail address from the start form – which is why step 2 mattered more than it looked. The message can be published from outside:

    curl -X POST /api/v1/messages -H 'Content-Type: application/json' \
  -d '{"name":"bw-rueckzug","correlationKey":"ada@example.org"}'
    Scope-RegelScope rule

    Was ein Subprozess in seinem eigenen Scope schreibt, verschwindet mit ihm. Der Vermerk status = "zurückgezogen" überlebt nur, weil eine ioMapping-Ausgabe am Subprozess ihn herausreicht.

    What a subprocess writes in its own scope disappears with it. The note status = "zurückgezogen" survives only because an ioMapping output on the subprocess hands it out.

  11. Publizieren – alles auf einmalPublish – everything at once

    Beim Publizieren prüft Atlas die Applikation als Ganzes: löst jede DMN-Referenz auf, bindet die Entscheidungen an die Business-Rule-Tasks, kompiliert beide Prozesse. Ein einziger Fehler – eine Entscheidung, die kein Modell liefert – weist den ganzen Bundle-Deploy zurück, statt ein halbes Release zu hinterlassen. Danach steht ein Release mit einer Versionsnummer und einer Momentaufnahme dessen, was ausgeliefert wurde.

    Publishing validates the application as a whole: every DMN reference is resolved, the decisions are bound to the business rule tasks, both processes are compiled. A single failure – a decision no model provides – refuses the entire bundle deploy instead of leaving half a release behind. What you get is a release with a version number and a snapshot of what shipped.

    POST /api/v1/applications                      → applicationId
POST /api/v1/dmn-models?name=bw-vorpruefung    → modelRef
POST /api/v1/dmnrefs        { projectId, modelRef }
POST /api/v1/forms          { id, projectId, schema }   × 3
POST /api/v1/drafts?projectId=…   <bewerbung.bpmn>, <interview.bpmn>

    Genau diese Reihenfolge geht auch der Knopf oben. Laufende Instanzen bleiben auf ihrer Version, bis du sie migrierst – ein Release ändert nie einen Fall, der schon unterwegs ist.

    That is the exact order the button above follows. Running instances stay on their version until you migrate them – a release never changes a case that is already under way.
