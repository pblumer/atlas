# Architecture Decision Records

This directory records the significant architectural decisions made on Atlas, using the [MADR](https://adr.github.io/madr/)-influenced format described in [`template.md`](template.md).

An ADR captures a decision, the context that forced it, the options considered, and the consequences accepted. ADRs are immutable once accepted: if a decision changes, a new ADR supersedes the old one rather than editing it.

A number belongs to exactly one decision. Take the next free one when you add a record — two branches each taking "the next number" is how 0090, 0103 and 0105 came to be shared by unrelated ADRs (the later record of each pair now lives at 0139, 0140 and 0141). `go test ./docs/adr` enforces unique, gapless numbers and keeps the index below in step with the directory.

A new shared `api/web/connectordialog.js` holds one dialog and `connectorShape(kind, provider)` — the single description of which fields a kind and provider use — so the Console's **Edit** stops being two `window.prompt` boxes and its create form stops keeping a second copy of the rules. Every incident row gains **⚙ Connector…** beside ✎ Fix variables…, opening prefilled with the runtime's own reason and a test button, with **Save & retry** writing the change and handing the job one more attempt; a name nobody configured has nothing to open, so it points at the Console. `PATCH /connectors/{id}` accepts `provider` (the field the question was literally about — re-creating under the same name would break every model referencing it) and re-runs the kind's full create validation on the patched record, so an unusable edit is refused where it is typed | Accepted |
| [0161](0161-element-io-on-the-diagram.md) | What an element was handed, on the diagram — reading a replay, the question about a task is *what went in and what came out*. ADR-0159 answered the output half in a tab; the input half did not exist at all: an activity's `zeebe:ioMapping` inputs are evaluated into its **activity-local** scope (ADR-0068), and the timeline folds only the process and subprocess scopes (ADR-0074), so the values a task was actually handed were durable but unreachable — the Properties panel could show `=order.amount * 2`, nothing could show that it came out as `100` here. A timeline step gains `inputs`: the element's own mapping locals as evaluated, scanned **only** for elements that declare mappings and filtered to the declared targets (an activity's local scope also holds a script result awaiting its output mapping, a multi-instance loop counter — not inputs), and deliberately kept out of `variables`/`variablesAfter`, since folding a local into the shared running set would leak it onto every concurrent step. In the replay, selecting an element hangs a small card under it: **in** from that field, **out** from the same diff that marks the Variables tab's `+` chips, so the two surfaces cannot tell different stories; *still running* is distinguished from *wrote nothing*. Capped at six rows a side, takes no pointer events, toggleable and remembered. Read-side only — no value type, event, column family or recovery path; the accepted cost is one store scan per io-mapped element instance on the timeline read | Accepted |
| [0162](0162-process-instance-migration.md) | Process instance migration — a deployed definition is immutable and versioned (ADR-0019), so a model fix reaches new instances only; the ones that *motivated* the fix stay bound to the old version through `ProcessInstanceValue.ProcessDefKey` and element indices into the old compiled graph, and the only ways out are cancel-and-restart (which discards work already done and re-runs side effects already committed) or repairing each instance by hand. The binding is deliberate — replay must reproduce state from the events alone (I4/I6) — so migration has to be **a durable event carrying a frozen element mapping**, never a matching recomputed during the fold: a fold that derived its mapping would depend on the algorithm's code, so improving that algorithm would silently rewrite history and two builds could disagree where a token is. Five parts. **Bindings, not lifecycle:** element instance keys, token ids, scope keys and boundary links are preserved, which is exactly what lets variables, data objects, jobs and the active-children counts ride through untouched — they key off element instance keys, not element indices. Ten live families are rewritten (element instances, timers, message/signal subscriptions, incidents, compensables, and the per-definition token/instance/start-key counters) — jobs dropped off that list when the engine-wide job-type table landed, leaving behind a check rather than a rewrite: a job carries the index of its type's *name*, so a task whose job type was renamed between versions would be left activatable under a type no worker subscribes to. **Validation is a gate that refuses**, not a heuristic that guesses: an unmapped active token, a changed BPMN type, an inconsistent scope chain, a multi-instance or event-gateway role change, a changed message/signal subscription identity (the name is in the *key*), an unmapped compensation handler, a leased job (overridable) — each rejects the command before anything is written. **History is not rewritten** — the steps under the old version happened under it, and an element the new version deleted could not be re-pointed anyway — so the *reader* changes instead: the timeline resolves each step through the definition in force at that step's log position, switching at the migration, which rides in ADR-0159's operator-action record (the seam it left open, plus one append-compatible field naming the definition migrated *from*) and so also shows up on the replay with its actor and reason. **One instance per event**, batched only at the API, mapping by BPMN element id with per-element overrides resolved to indices before the log (I5). Rejected: cancel-and-restart (not a migration), recompute-in-the-fold (breaks I4 outright), and redeploying over the same definition key, which performs an unvalidated migration on every instance at once and destroys the immutability the replay rests on | Proposed |
| [0163](0163-no-in-process-service-tasks.md) | No in-process service tasks — the core loop must never be able to get stuck. ADR-0156 kept in-process execution as a legitimate rung for "one short call to an infrastructure-grade endpoint"; with ADR-0157's seven steps delivered, that position no longer holds. It rests on a promise the model cannot make and the engine cannot check — that someone else's host stays fast — settled against the one goroutine the whole engine shares. Three things decide it: the promise is **unenforceable** (nothing rejects a slow endpoint, and the endpoint that was fast at authoring time is the one that is down at 3am; ADR-0149's ten-second budget is simultaneously far too long to be invisible and far too short for some real integrations); the alternative is **no longer expensive** (`--supervise` runs the workers from the same binary, so ADR-0156's "destroys the single-binary experience" objection is spent); and step 6 made in-process **survivable, not right** — handlers off the run loop remove the catastrophe, but the engine's own process is still not the place to run someone else's integration, competing for its CPU and file descriptors, sharing its address space and credentials, dying with it. **The rule: every side-effecting service task belongs on a worker; Atlas's process runs the engine and not integrations.** What cannot block is untouched — the FEEL script task, local DMN, the mockup task — because this is about side effects, not computation. Reached by **deprecation, not removal**: the connector kinds keep working and no running installation is disturbed, but they are transitional, new kinds are built worker-first, and the Workers view's in-process marking becomes the notice. The honest gap, found while building `atlas worker` and stated rather than glossed: a connector task **cannot** run on a worker yet, because every connector handler resolves its configuration from the compiled process through a local `ProcessLookup` an external process does not have. Closing it means the task detail travelling *with the job*; until then only a model-authored job type can actually be relocated, which is also why removal is rejected for now — banning what has no replacement would break every deployment | Accepted |
